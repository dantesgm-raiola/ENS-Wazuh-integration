# ENS dashboards for Wazuh 5.x

Two OpenSearch Dashboards saved-object bundles. They replace the 4.x dashboards, which read
`wazuh-alerts-*` and the `ens-sca-checks` index filled by the removed sync script. On 5.x
both data sources are written natively by Wazuh, so nothing extra has to run:

| File | Reads | Shows |
|---|---|---|
| `ens_sca_compliance_5x.ndjson` | `wazuh-states-sca*` | ENS configuration compliance from the `ens_linux` / `ens_windows` SCA policies |
| `ens_detections_5x.ndjson` | `wazuh-findings-v5-*` | Findings from the ENS detection rules (`rules/`) |

Both files are generated by `build_dashboards.py` (Python 3, stdlib only). Edit the script, not
the ndjson, then regenerate:

```bash
python3 dashboards/build_dashboards.py          # rewrite both ndjson files
python3 dashboards/build_dashboards.py --check  # validate, and fail if the files are stale
```

Every object id starts with `ens-5x-`, including the two index patterns the bundles bring with
them (`ens-5x-states-sca` → `wazuh-states-sca*`, `ens-5x-findings` → `wazuh-findings-v5-*`).
They don't touch Wazuh's own index patterns or the old 4.x `ens-*` objects. Delete those old
objects by hand if they're still in your dashboard.

## Importing

In the dashboard, open **Dashboards Management → Saved objects → Import**, choose a file, and
allow it to overwrite conflicts (only `ens-5x-*` objects are affected).

Or use the API. This is an example, so adjust the host and credentials:

```bash
curl -s -u admin -X POST "https://<dashboard-host>/api/saved_objects/_import?overwrite=true" \
  -H "osd-xsrf: true" \
  --form file=@dashboards/ens_sca_compliance_5x.ndjson
```

The index patterns ship with an empty field list. If a panel says a field is missing, open the
pattern under **Dashboards Management → Index patterns** and refresh its fields.

## Tagging conventions the panels depend on

The `wazuh-states-sca` mapping is strict, and its `check.compliance` field accepts only
`cmmc, fedramp, gdpr, hipaa, iso_27001, nis2, nist_800_171, nist_800_53, pci_dss, tsc`. The
agent drops any other key, including the `ens`/`ens_nivel` keys the 4.x policies used. ENS
metadata is therefore carried in `check.references`, as plain strings:

| Entry | Example | Used by |
|---|---|---|
| `ens:<control>` | `ens:op.acc.6` | per-control panels (terms with include `ens:.*`) |
| `ens-level:<level>` | `ens-level:basico` | per-level panel (include `ens-level:.*`) |
| `iso27001-2022:<ctrl>` | `iso27001-2022:8.5` | not charted. Kept for search and crosswalks. |

Detection rules carry the same information in `wazuh.rule.tags` (`ens.op.acc.6`,
`iso27001-2022.8.5`). The detections dashboard is scoped to `wazuh.rule.tags: ens.*`.

If a check or rule doesn't follow these conventions, it won't appear in the per-control and
per-level panels.

## SCA compliance dashboard (`ENS — SCA compliance (Wazuh 5.x)`)

Scoped to `policy.id: (ens_linux or ens_windows)`. `wazuh-states-sca` is a state index with no
time field, so it always shows the current result of every check and the time picker does
nothing.

| Panel | What it shows |
|---|---|
| Policy filter | Drop-down on `policy.id` that filters every panel |
| Check results | Counts of Passed / Failed / Not applicable |
| Agents assessed | Distinct agents with ENS results, and the newest `state.modified_at` |
| Result distribution | Donut of `check.result` |
| Compliance % by policy | Passed ÷ (Passed + Failed) per policy; Not applicable excluded |
| Compliance % by ENS level | Same ratio per `ens-level:*` |
| Compliance % by ENS control | Same ratio per `ens:*` control |
| Results by ENS control | Control × result: check results and distinct agents |
| Compliance % by agent | Pass ratio per agent |
| Results by agent | Agent × policy × result counts |
| Failed checks by agent and ENS control | Where each agent fails |
| Most failed checks | Checks failing on the most agents |
| Failed checks (search) | Agent, policy, check id, name and `check.reason` for every failure |
| Not applicable checks (search) | Checks the agent couldn't evaluate, with the reason |

If **Not applicable** results say `Remote commands are disabled for this policy`, that agent
doesn't have `sca.remote_commands=1` set. The command (`c:`) checks in a policy pushed through
a group are skipped without it (see the main README).

## Detections dashboard (`ENS — Detections (Wazuh 5.x)`)

Scoped to `wazuh.rule.tags: ens.*` and driven by the time picker (`@timestamp`). It stays empty
until the ENS rules are promoted to the Custom space and added to a detector.

| Panel | What it shows |
|---|---|
| Findings | Number of ENS findings and distinct agents in range |
| Findings over time | Findings per interval, split by `wazuh.rule.level` |
| By level | Donut of rule level |
| By ENS control | Findings per `ens.*` tag |
| By agent | Agents with the most findings and the controls they hit |
| Top rules | Rules by finding count, with agent count and level |
| Recent findings (search) | Latest findings: agent, rule, level, tags |

## Status

The JSON is checked offline: every line and nested JSON string parses, every reference resolves,
ids are unique, and panels fit the 48-column grid. Both bundles were deployed to a production
Wazuh 5.0.0 dashboard on 2026-11-25, written straight into `.kibana` with the indexer admin
certificate (the same raw saved-object shape the Import API stores). Both index patterns then got
their field lists from `_field_caps`. `wazuh.rule.tags`, `wazuh.rule.title`, `check.references`,
`check.result` and `policy.id` are all aggregatable keywords. Still to check by eye in the UI:
- the `include` regex on the terms aggregations
- the input-control panel against a pattern with no time field
