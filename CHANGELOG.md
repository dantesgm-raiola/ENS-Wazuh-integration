# Changelog

## [Unreleased — Wazuh 5.x] (branch `wazuh-5.0-migration`)

Port to Wazuh 5.x. Nothing on this branch installs on Wazuh 4.x. Full rationale and upgrade
steps: [docs/MIGRATION_5x.md](docs/MIGRATION_5x.md).

### Changed
- SCA policies use the 5.x format: `name` instead of `title`; ENS control, level and
  ISO 27001:2022 control moved from `compliance` (`ens`, `ens_nivel`, `iso_27001`, which the 5.x
  agent drops) to `references` (`ens:<control>`, `ens-level:<level>`, `iso27001-2022:<control>`);
  `compliance` now holds a family-level `nis2` mapping only.
- sshd checks read the effective configuration (`sshd -T`), so `sshd_config.d/` drop-ins and
  defaults count. KEX/cipher/MAC checks now fail on weak algorithms instead of passing on any value.
- Kernel parameters, binaries and daemons are checked through `/proc/sys`, `f:` and `p:` rules:
  command rules dropped from 56 to 28 Linux checks.
- Windows password/lockout checks use `secedit` like the stock 5.0 CIS policies (the old
  `Netlogon\Parameters` reads never held those settings).
- `install.sh` targets `/var/wazuh-manager`: registers `ens-linux`/`ens-windows` with
  `agent_groups`, places the policies in the group directories, writes a per-group `agent.conf`,
  and optionally adds agents (`--linux-agents`, `--windows-agents`). No API credentials, no
  `ossec.conf` edits, refuses to overwrite a group `agent.conf` it didn't write.
- Detection rules rewritten as Sigma rules for the content manager (`rules/ens-*.yml`), on Wazuh
  Common Schema fields seen in real events, tagged `ens.<control>`. Deployed by
  `tools/deploy_rules.py` (dry-run / read-only plan / `--apply`).
- Dashboards rebuilt on `wazuh-states-sca*` and `wazuh-findings-v5-*`, generated by
  `dashboards/build_dashboards.py`.
- `tests/validate_sca.py` validates against what the 5.x agent accepts.

### Fixed
- `install.sh`/`uninstall.sh` write to the group directories the manager actually reads.
  5.0.0-1 builds published from late October 2026 on read `/etc/wazuh-manager/shared/`; the
  scripts wrote to `/var/wazuh-manager/etc/shared/`, which those builds ignore, so the policy
  never reached agents. The directory is now detected (`WAZUH_CONF_DIR` overrides).
- The `ens-windows` group `agent.conf` pointed Windows agents at `etc/shared/ens_windows.yml`.
  Windows agents keep group files in `shared\` (no `etc\`), so the policy was never loaded.
  It is now `shared/ens_windows.yml`.
- `--groups` sent active Windows agents with an empty `os_platform` to the "never connected"
  skip list; the OS family now comes from `os_type` first.
- A new ENS group no longer gets a `.bak` of the stock `agent-template.conf` that
  `agent_groups` seeds it with, and `--force` backups go to `<config dir>/ens-install-backups/`:
  any file left in a group directory is pushed to that group's agents.
- `install.sh --help` no longer prints the `set -euo pipefail` line.
- Directory rules that were meant to read file contents only matched file names (30021 sudoers.d,
  30022 profile.d umask, 30131 rsyslog.d, 30400 profile.d TMOUT).
- False passes: antimalware satisfied by the Wazuh agent (30110), "backup" satisfied by rsync
  (30510), SELinux permissive (30103), `ClientAliveCountMax 0` (30031), any TMOUT value (30400).
- False fails: Debian 13 without rsyslog (30130/30131), missing `lastlog` (30124), `chrony` unit
  name (30126), ESET-protected Windows (31100), secure-by-default absent values (31033, 31102),
  `RunAsPPL=2` (31035), Windows 10+ update settings (31700).
- Windows checks reading the wrong place: event log service (31120), per-user screensaver under
  the SYSTEM hive (31400, now the machine inactivity limit).
- Detection rules: every rule now targets the event it describes (the 4.x versions swapped sudo
  success/failure, labelled every SSH auth failure "weak cipher", and lowered the severity of
  stock auditd and attack rules).

### Removed
- `tools/sync_sca_to_opensearch.py`, `install_sync.sh`, `uninstall_sync.sh`: 5.x indexes SCA
  results natively and has no `/sca` API. The tool also logged password prefixes.
- `sca/ens_windows_remote.yml`, `tools/collect_registry.py`: the agentless Windows workaround
  for a 4.14 manager bug isn't needed on 5.x, and reused `ens_windows.yml` check IDs.
- `deploy_sca_agents.sh` (folded into `install.sh`), `tests/diagnose_sca.sh` (4.x paths).
- Check 31101 (merged into 31100).

### Added
- `install.sh --groups g1,g2`: adds every current member of existing Wazuh groups to
  `ens-linux`/`ens-windows` by OS (read from the manager's agent database), without touching
  those groups' files. Agent IDs are validated before any change, existing memberships are
  skipped, and a failed `agent_groups` call now stops the install (the tool exits 0 on errors).
- `tools/agent_enable_sca_commands.sh` / `.ps1` to set `sca.remote_commands=1` on agents.
- `docs/MIGRATION_5x.md`, `docs/detection_rules_5x.md`, `dashboards/README.md`.

### Verified on a live 5.0.0 deployment (2026-11-25/26)
- Rule deployment through the content manager and both detectors: findings match source events.
- Dashboards written as saved objects, with index-pattern fields refreshed.
- `install.sh --groups default,servers,proxmox` on the `/etc/wazuh-manager` layout: 12 agents
  went to `ens-linux` and 24 to `ens-windows`. Both policies reached `wazuh-states-sca` from real
  agents: 60 checks per Linux agent, 17 per Windows agent.
- Command checks report "Not applicable" until `sca.remote_commands=1` is set on the agent.

### Not yet verified
- Command checks with `sca.remote_commands=1` enabled.
- Dashboard panels against a full fleet of results (only checked against early results).

## [Unreleased — 4.x]

### Added
- `docs/iso27001_mapping.md`: compatibility note documenting that Wazuh's own native ISO 27001 module (`wazuh-dashboard-plugins#8286`) uses ISO/IEC 27001:2013 numbering internally, while this project uses 2022 — flagged so the two don't get confused if run side by side.
- `rules/ens_detection_rules.xml`: each `ISO27001_<control>` group is now paired with a lowercase `iso_27001_<control>` token, matching the naming convention Wazuh's own bundled ruleset uses for other frameworks (`pci_dss_11.4`, `gdpr_IV_35.7.d`, `tsc_CC6.1`, ...). Purely additive, low-cost hedge in case a future Wazuh dashboard release enriches compliance fields from that pattern — not confirmed to have any effect today.

### Fixed
- Removed 6 pre-existing panels from `ens_dashboard.ndjson` (`ens-viz-by-level`, `ens-viz-top-failing`, `ens-viz-sca-by-family`, `ens-viz-compliance-pct-bar`, `ens-viz-control-detail-table`, `ens-viz-agent-control-table`) that queried `data.sca.type: check` against `wazuh-alerts-*`. Wazuh only writes an individual check event there on the first scan or on a pass/fail state change — never a full snapshot — so these panels showed sparse, inconsistent data depending on the selected time range (regression from an earlier fix in this same history; see commit `6206583`). The main dashboard now only uses `data.sca.type: summary` and detection-rule alerts, both of which Wazuh indexes reliably.
- Per-control compliance detail (for both ENS and the new ISO 27001:2022 tagging) is now exclusively in `ens_sca_checks_dashboard.ndjson` (Phase 2), which is fed a full snapshot on every run by `tools/sync_sca_to_opensearch.py` and does not have the sparsity problem above.
- `tools/sync_sca_to_opensearch.py`: added `iso_27001` to the `ens-sca-checks` index mapping as `keyword`.
- `tests/validate_sca.py`: warns if a check is missing the `iso_27001` compliance tag.

### Added
- ENS ↔ ISO/IEC 27001:2022 controls mapping (`docs/iso27001_mapping.md`), covering both automated and manual-evidence ENS controls
- `iso_27001` compliance tag added to all 96 SCA checks (`ens_linux.yml`, `ens_windows.yml`, `ens_windows_remote.yml`), alongside the existing `ens`/`ens_nivel` tags
- `ISO27001_<control>` groups added to all 25 tagged detection rules in `ens_detection_rules.xml`, alongside the existing `ENS_<control>` groups
- `ens_sca_checks_dashboard.ndjson` (Phase 2 check-level dashboard): ENS and ISO 27001:2022 compliance % by control, per-control detail table, per-agent drill-down for both frameworks, and an ENS↔ISO 27001 crosswalk table validated against live check data
- Initial SCA policy for Linux (`ens_linux.yml`) with 40+ checks covering op.acc, op.exp, op.mon, mp.com, mp.eq, mp.info, mp.s, mp.sw
- Initial SCA policy for Windows (`ens_windows.yml`) with baseline checks
- Detection rules (`ens_detection_rules.xml`) mapping existing Wazuh events to ENS controls
- Automated installer and uninstaller scripts
- Full ENS ↔ Wazuh controls mapping reference (`docs/controls_mapping.md`)
- SCA policy validation script (`tests/validate_sca.py`)
- GitHub Actions CI workflow for syntax validation
- **20 new SCA checks** across Linux and Windows (see breakdown below)
- **Remote/agentless Windows mode** (`sca/ens_windows_remote.yml` + `tools/collect_registry.py`):
  - Workaround for Wazuh SCA engine regression in 4.14.x that rejects `r:HKLM\...` rules on Linux managers (tracked upstream at [wazuh/wazuh#28979](https://github.com/wazuh/wazuh/issues/28979))
  - Covers the same 9 ENS checks (IDs 31010–31700) using `f:` rules against a local registry snapshot
  - Collector script supports WinRM (primary) and SSH (fallback) with single-host and batch modes
  - Policy is skipped silently if no snapshot file is present — no false positives
